**Дата:** 20.10.2026 · **Кто:** Земля · **Статус:** **v1 утверждён Славой 20.10** (с правками — раздел «Решения Славы» внизу). По нему работают Земля (агент) и Воздух (облако).

Задача — [часть L](/stand/agent-cloud-mode), план — [первый клиент Bilem Cloud](/stand/pervyj-klient-darya). Агент — Земля, облако (`app.bilem.ai`, `mcp.bilem.ai`) — Воздух. Версия протокола — `v1` в пути, несовместимые изменения — `v2`.

## Коротко

1. Человек нажимает «Подключить…» у базы → агент создаёт **заявку** в облаке и открывает кабинет.
2. Человек входит в кабинет, подтверждает, видит **код** (8 символов, 10 минут, один раз).
3. Код вводится в агент → агент меняет его на **ключ компьютера** (первый раз) и **привязку базы** к организации.
4. Служба агента держит **одно исходящее соединение** (WebSocket по TLS) к `mcp.bilem.ai`. По нему облако присылает вызовы инструментов MCP — только к привязанным базам; агент отвечает результатом.

Входящих портов на компьютере клиента нет. Ничего, кроме ответа на конкретный вызов, агент в облако не отправляет.

## Сущности

| Что | Кто выдаёт | Где хранится |
| --- | --- | --- |
| `agent_id` — номер установки агента (GUID) | агент, при первом включении Bilem Cloud | конфиг агента |
| **ключ компьютера** `agent_key` — 32 случайных байта, base64url | облако, при первом обмене кода | агент: секреты (DPAPI LocalMachine), не в логах/sysinfo/отчётах. Облако: только хеш SHA-256 |
| `base_id` — номер базы (GUID) | агент, при первом «Подключить…» этой базы | конфиг агента, у базы |
| **привязка** база → организация в облаке | облако, при обмене кода | облако (и копия списка в агенте) |
| `request_id`, **код** | облако, на заявку | облако; код — у человека в кабинете |

**Один ключ на компьютер + привязки баз** (утверждено). Ключ отвечает на «какой это компьютер», привязка — «какую базу какая организация разрешила». Отключить одну базу — снять привязку, ключ не трогаем.

Базы одного компьютера **могут принадлежать разным организациям** в облаке (аутсорсинговая бухгалтерия: сто баз — сто клиентов). Канал один на компьютер, облако разводит вызовы по привязкам.

## 1. Заявка на подключение базы

Агент → `POST https://mcp.bilem.ai/agent/v1/connect-requests` (с заголовком `Authorization: Bearer <agent_key>`, если ключ уже есть).

Тело (JSON): `agent_id`, `agent_version`, `machine` (имя компьютера), `login_hint` (e-mail, который человек ввёл в агенте; можно пусто), `base`: `base_id`, `slug`, `configuration` (имя и версия конфигурации), `organizations` — список организаций базы: **наименование и БИН/ИИН**. Данных учёта в заявке нет.

**БИН/ИИН — только для подключения** (решение Славы, см. ниже): облако использует его, чтобы опознать базу и сверить с организацией в кабинете, в открытом виде не хранит и нигде не показывает.

Ответ 201: `request_id`, `connect_url` (`https://app.bilem.ai/connect?r=<request_id>`), `expires_at` (+10 минут). Агент открывает `connect_url` в браузере.

## 2. Кабинет (сторона Воздуха)

Вход Google / Microsoft → «Компьютер **BUH-SERVER** просит подключить базу **…** (в базе: ТОО «…») к вашей организации» → выбор организации (если их несколько) → проверка лимита баз по тарифу → **код**: 8 символов, алфавит Crockford base32 без похожих (`0/O`, `1/I/L`), показ `XXXX-XXXX`. Код живёт 10 минут, привязан к `request_id`, одноразовый. Лимит исчерпан — кабинет говорит это сам, код не выдаёт.

В кабинете организации из базы показываются **только по названию**, без БИН/ИИН.

**`login_hint` ≠ вошедший аккаунт** (найдено в тесте #58, сделано в #60): кабинет крупно пишет «Агент указал `X`, а вы вошли как `Y`. Подключить базу в организацию `<имя>`?». Кнопок две. «Выйти и войти другим аккаунтом» ведёт на logout → вход: страница подсказывает `X` и передаёт его в Auth0 как `login_hint`, после входа человек возвращается на ту же заявку. «Всё верно, подключить сюда» открывает выбор организации. Если организаций несколько, по умолчанию выбрана та, где есть участник с e-mail `X`. Облако сохраняет `login_hint` в привязке базы. Если он отличается от того, кто подтвердил, в «1С-Базы → Bilem Cloud» видно «подключил `Y`, в агенте указан `X`». Поле протокола не менялось: агент шлёт `login_hint` из `cfg.Cloud.LoginHint` (сверено с `CloudApi.cs`).

## 3. Обмен кода

Агент → `POST /agent/v1/connect-requests/{request_id}/exchange`, тело: `agent_id`, `code` (дефисы и регистр не важны). Если ключ уже есть — с `Authorization: Bearer <agent_key>`.

Ответ 200: `base_id`, `org` (`id`, `name`, `mcp_url` — вида `https://mcp.bilem.ai/<org>`), `login` (e-mail, кто подтвердил), и **`agent_key` — только если у компьютера ключа ещё не было**.

| Ошибка | HTTP | `error` | Агент пишет |
| --- | --- | --- | --- |
| неверный код | 400 | `code_invalid` | «Код не подходит — проверьте и введите ещё раз» (попыток на заявку — 5) |
| истёк | 410 | `code_expired` | «Код устарел — нажмите «Открыть ещё раз»» |
| уже использован | 409 | `code_used` | «Код уже использован — получите новый в кабинете» |
| попыток больше 5 | 429 | `too_many_attempts` | «Слишком много попыток — начните подключение заново» |
| ключ отозван | 401 | `key_revoked` | агент удаляет ключ, просит подключить базы заново |

Ошибки — всегда JSON `{"error": "…", "message": "текст для человека"}`.

## 4. Канал службы

**Транспорт — WebSocket по TLS:** `wss://mcp.bilem.ai/agent/v1/channel`, заголовки `Authorization: Bearer <agent_key>`, `X-Bilem-Agent: <agent_id>`. Почему не долгий HTTP: вызовы идут от облака к агенту, ответ нужен за секунды, вебсокет даёт это одним соединением с пингом. Прокси Windows агент учитывает (системный прокси, учётка компьютера). Резерв на случай прокси, режущего вебсокет, — долгий опрос HTTP в `v2`, если понадобится.

Сообщения — JSON-текст, поле `type`:

| `type` | Кто → кому | Поля |
| --- | --- | --- |
| `hello` | агент → облако, первым | `agent_id`, `agent_version`, `machine`, `bases`: список `{base_id, slug, tools}` (имена инструментов) |
| `welcome` | облако → агент | `ping_interval` (с, по умолчанию 25), `bases`: `{base_id, state, reason, org}` |
| `call` | облако → агент | `id` (GUID), `base_id`, `caller` (`channel`: whatsapp/telegram/chatgpt/claude/…, `user`: кто спросил — для журнала), `deadline_ms` (по умолчанию 60000), `rpc` — запрос MCP JSON-RPC (`tools/list` или `tools/call`) |
| `result` | агент → облако | `id`, `rpc` — ответ MCP JSON-RPC как есть |
| `cancel` | облако → агент | `id` — человек ушёл, результат не нужен |
| `base_state` | облако → агент | `base_id`, `state`, `reason` — смена состояния без переподключения |
| `bases` | агент → облако | полный список баз после изменений на компьютере (подключили / отключили / удалили базу) |
| `ping` / `pong` | обе стороны | `t` — время отправителя |

**Правила агента (проверяет агент, даже если облако ошиблось):**

- `call` к `base_id`, которого нет среди привязанных и включённых в агенте, — ответ `rpc.error` «база не подключена к облаку», в журнал.
- Аргумент `base` в вызове агент **ставит сам** по `base_id`; что прислало облако в `base`, игнорируется. `list_bases` и `tools/list` — только по этой базе.
- Дальше — те же правила, что у локального MCP: «Доступ» (чтение, белый список записи), аудит с `caller`.
- Одновременно — до 4 вызовов на компьютер, остальные в очереди; дедлайн вышел — `rpc.error` «превышено время», 1С не дёргаем дальше по возможности.
- Ответ больше 8 МБ — `rpc.error` «ответ слишком большой — сузьте запрос».

**Состояния базы** (`state`): `active` — работает; `paused` (`reason`: `unpaid`, `limit`) — «На паузе — проверьте кабинет», вызовы к ней облако не шлёт; `revoked` (`reason`: `cabinet`) — «Отключена в кабинете», агент снимает у себя привязку.

**Закрытие соединения облаком** (коды WebSocket): `4401` — ключ неверен или отозван (агент удаляет ключ, переподключение не пытается, статус «Ключ отозван — подключите базы заново»); `4409` — с этим `agent_id` открыто другое соединение (второй экземпляр/клон машины — в журнал, переподключение через 5 минут); `4429` — слишком часто; `1012` — облако перезапускается.

**Переподключение** — само: паузы 1, 2, 5, 10, 30, 60 с, дальше раз в 5 минут, со случайной добавкой. Нет `pong` 3 интервала подряд — соединение считается мёртвым. Статус «Нет связи с облаком» + время последней связи.

## 5. Отключение и выключение

- **Отключить базу в агенте** → `DELETE /agent/v1/bases/{base_id}` (с ключом) + сообщение `bases`. Привязка снята, лимит в кабинете освободился.
- **Отключить в кабинете** → облако шлёт `base_state` `revoked`; агент показывает «Отключена в кабинете».
- **Снять галочку Bilem Cloud** в агенте → агент закрывает канал (код `1000`, причина `mode_off`), привязки и ключ сохраняются; вернули галочку — канал открывается без кода, облако отвечает `welcome` с прежними привязками.
- **«Удалить компьютер» в кабинете организации** → снимаются **только привязки этой организации**. Ключ компьютера отзывается (закрытие `4401`), только когда у компьютера не осталось ни одной привязки — или через поддержку. Иначе один клиент бухгалтерской фирмы отключил бы базы всех остальных.
- **Удаление агента** → ключ стирается вместе с данными агента; привязки в облаке остаются до отзыва в кабинете (кабинет показывает «нет связи с … дней»).

## Безопасность

- Только TLS, проверка сертификата обычная (без своих исключений). Ключ — в заголовке, не в адресе.
- Облако хранит хеш ключа; код — одноразовый, 10 минут, 5 попыток.
- Агент в облако шлёт только: заявку (имя компьютера, база, конфигурация, организации базы — название и БИН/ИИН), `hello`/`bases` (список привязанных баз и имена инструментов), ответы на вызовы. Никакой фоновой выгрузки.
- Ответы инструментов проходят через облако и отдельно **не хранятся** — только внутри переписки с агентом, по сроку из политики конфиденциальности (по умолчанию 24 часа, клиент меняет от 0 до 30 суток).

## Облачная сторона — статус (Воздух, 22.10.2026)

Карточка #56 на доске stand. **Сделано в коде, не задеплоено** — `skp-kz/minidesk`, коммит `b3a7b99`, проект `bilem-app`:

- **HTTP-часть протокола** (разделы 1, 3, 5): `POST /agent/v1/connect-requests`, `POST /agent/v1/connect-requests/{id}/exchange`, `DELETE /agent/v1/bases/{base_id}` — поля и коды ошибок как в таблице выше, сверено с `CloudApi.cs` агента. Дополнительные ошибки: `not_approved` (409, код ещё не выдан в кабинете), `limit` (402), `base_conflict` (409, база уже подключена с другого компьютера), `request_not_found` (404). У всех есть `message`.
- **Кабинет** `app.bilem.ai/connect?r=…` (раздел 2): компьютер, база, организации базы только по названию; выбор организации (подключать может владелец или администратор); лимит баз по тарифу; сверка БИН/ИИН по HMAC с уже подключёнными базами организации и предупреждение «базу другой компании»; код `XXXX-XXXX` на 10 минут, кнопка «Получить новый код». Старый код после неё не работает. Заявку можно открыть в течение часа: так «Открыть ещё раз» в агенте работает и после устаревшего кода.
- **Кабинет → 1С-Базы → вкладка «Bilem Cloud»**: базы в облаке, «Отключить» и «Удалить компьютер». «Удалить компьютер» снимает только привязки этой организации; ключ отзывается, только если у компьютера не осталось привязок.
- **Хранение**: ключ компьютера — SHA-256, код и БИН/ИИН — HMAC (секрет `CLOUD_SECRET`, пока его нет — производный от `SESSION_SECRET`). Миграция `bilem-app/migrations/2026-10-22-cloud-connect.sql`.
- **Ключ без Bearer**: если в облаке ключ у компьютера уже есть, а агент пришёл без него (переустановка, отозванный ключ), то после подтверждения кодом облако выпускает новый ключ, а старый перестаёт работать.
- **Проверка**: `cd bilem-app && node tools/test-cloud-connect.mjs` — 26 проверок на `node:sqlite`.

**Канал (раздел 4) — сделан в коде, не задеплоен** (карточка #59, коммит `3f1be18`): Worker `bilem-mcp` (`minidesk/tools/bilem-mcp`) на `mcp.bilem.ai`, Durable Object на компьютер с WebSocket Hibernation. Ключ проверяется до апгрейда, неверный — закрытие `4401`. `hello` → `welcome` (`ping_interval` 25, состояния баз из D1, `org`: `{id, name}`), `call`/`result`/`cancel` (дедлайн 60 с + 2 с на дорогу, потом `cancel`), `base_state` сразу при отключении в кабинете, `bases` → `base_state` для неактивных, `ping` → `pong` с тем же `t`. Остальное `/agent/v1/*` Worker проксирует в Pages, как раньше. Пока Worker не задеплоен, `/agent/v1/channel` отвечает 503 `channel_unavailable`.

**Уточнения к протоколу — на согласование Славе:**

- `4409`: новое соединение **вытесняет старое** (старое закрывается `4409`). После обрыва сети старое соединение часто остаётся полуоткрытым, и отказ новому оставил бы агента без связи. Клон машины получает `4409` и по протоколу возвращается через 5 минут.
- `4429`: больше 6 подключений за минуту.
- `welcome`/`base_state`: для базы, которой облако не знает, — `revoked` с `reason: unknown`. Для базы, отключённой самим агентом (`DELETE`), — `revoked` с `reason: agent`.

## Заглушка для разработки

До готовности облака агент работает с **заглушкой** по этому протоколу: адрес облака меняется в конфиге агента (на стенде — `127.0.0.1`), заглушка выдаёт код сама и шлёт вызовы. На ней — тесты части L: переключение режимов (локальный порт закрыт в Cloud), вызов к неподключённой базе — отказ, просроченный и повторный код, пауза, потеря связи и возврат.

## Решения Славы 20.10

1. **Один ключ на компьютер + привязки баз** — да. Плюс правило «Удалить компьютер» в кабинете снимает только свои привязки (раздел 5).
2. **Логин в агенте** — в таблицу баз добавить колонку «Организация в облаке» (к какому кабинету подключена база); поле «Логин» остаётся подсказкой для нового подключения.
3. **Названия организаций и БИН/ИИН в заявке** — отправлять. Правила для облака (Воздух):
   - БИН/ИИН используется **только для подключения**: опознать базу и сверить с организацией в кабинете (совпал — предложить её; не совпал — предупредить «вы подключаете базу другой компании»);
   - **в открытом виде не хранится**: после обработки заявки остаётся только ключевой хеш (HMAC с секретом облака) — чтобы узнать ту же базу при повторном подключении; сам номер облако не видит;
   - **в кабинете не показывается** — организации только по названию («ТОО «Ласточка»», «ИП Примин»);
   - БИН для счёта на оплату — отдельный реквизит, его клиент вносит сам (платить может другое юрлицо).
   - В политике конфиденциальности — строка о том, что БИН/ИИН используется для подключения базы и не хранится в открытом виде.
4. **Предел ответа 8 МБ и дедлайн 60 с** — да.
5. **Хранение ответов инструментов** — отдельно не храним, только в переписке по сроку из политики (раздел «Безопасность»).
6. **Для Воздуха:** вызовы с отправкой (`send_document`) облако пропускает, только если человек из канала (WhatsApp/Telegram) есть в белом списке организации; агент со своей стороны проверяет свой белый список записи.
7. **Где сервера.** Если когда-нибудь потребуют хранить данные в Казахстане — переезд облака на казахстанские серверы; сейчас не делаем.
