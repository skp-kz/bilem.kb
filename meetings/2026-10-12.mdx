<Note>
  **Это сценарий, а не факт.** Вопрос Славы: как развивать Bilem.ai, *если* официальный MCP-коннектор (`mcp.bilem.ai`) уже есть и приложение полгода обкатано на живой группе клиентов. Сейчас по [дорожной карте](/product/roadmap) мы на этапе 1 (cfe). Данных реального пилота у агентов не было — позиции опираются на роль и описание задачи.
</Note>

**Участники:** arman (CMO), Dev (CTO), Wiki Maintainer. bilem-earth (инженер) позицию не дал — его HTTP-адаптер не проснулся, задача SKP-12 в `blocked`.

## Главное

Все трое сошлись в одном: **после пилота расти мешают не функции, а повторяемость.** Нужно превратить полгода ручной работы в то, что масштабируется без людей:

1. **Подключение 1С без инженера** (CTO) — сейчас каждая база своя, подключение руками.
2. **Один доказанный сценарий и чёткий ICP** (CMO) — MCP сам по себе не покупают, покупают решённую задачу.
3. **Опыт пилота — в базу знаний** (Wiki) — пока он в головах и переписке.

## Топ-инициативы на 3 месяца

<Steps>
  <Step title="Самоподключение 1С — CTO" icon="plug">
    Мастер: тип базы → автопроверка доступа → определение конфигурации и версии → тестовый запрос «остаток денег» → готово. Готовое расширение `.cfe` для баз без OData.

    **Эффект:** подключение с 1–3 дней до < 30 мин; ≥ 70% клиентов без инженера.
  </Step>
  <Step title="Безопасность доступа к 1С — CTO" icon="user-shield">
    Технический пользователь 1С только на чтение по умолчанию; запись (счета, акты) — отдельное право + подтверждение в чате. Журнал всех запросов к 1С, изоляция клиентов, OAuth для MCP, ротация ключей. Стыкуется с [0006 · права в 1С](/decisions/0006-prava-v-1c).

    **Эффект:** проходим проверку ИБ/бухгалтерии клиента — основа для B2B и тарифа Pro.
  </Step>
  <Step title="Надёжность и наблюдаемость — CTO" icon="chart-line">
    Трассировка WhatsApp/MCP → LLM → tool → 1С (время, ошибка, токены, стоимость), дашборд по клиенту, алерт о недоступной базе раньше клиента, кэш справочников, очередь для тяжёлых отчётов.

    **Эффект:** SLO 99,5%, p95 < 8 с на простые вопросы.
  </Step>
  <Step title="Две траектории: Pro и Developer — CMO" icon="layer-group">
    Pro — готовые бизнес-сценарии, онбординг, поддержка. Developer — MCP/API, sandbox, документация, логи, лимиты. Одно посадочное сообщение RU + KZ с одним CTA «заявка на пилот/демо».

    **Эффект:** сравнимые activation и demo→pilot по сегментам вместо смешанных лидов.
  </Step>
  <Step title="Партнёрский тест: бухгалтеры и 1С-франчайзи — CMO" icon="handshake">
    10 проблемных интервью → 3–5 партнёров с referral-kit, чек-листом внедрения и своей атрибуцией. MCP-маркетплейсы — как каталог доверия, каналом считать только после отслеживаемых установок/демо.
  </Step>
  <Step title="Пилоты → кейсы — CMO" icon="file-lines">
    «Было → сценарий → время до первого результата → измеримый итог», FAQ по безопасности и интеграциям, RU/KZ. WhatsApp — для follow-up после демо, не для рассылок.
  </Step>
  <Step title="Знания пилота в базу — Wiki" icon="book">
    Месяц 1: разбор пилота (обращения, заметки, логи MCP → страницы по клиентам + «уроки пилота»). Месяцы 1–2: 15–25 типовых сценариев 1С по шаблону «задача → инструменты MCP → ограничения → пример диалога» + FAQ на 30–50 реальных вопросов. Месяцы 2–3: справочник MCP для разработчиков, quickstart «Bilem к своей 1С за час», матрица совместимости, changelog.

    **Эффект:** −30–40% повторных обращений; партнёры подключаются сами.
  </Step>
</Steps>

## Чего не делать

- Не давать модели писать в 1С без подтверждения пользователя и лимитов (сумма, тип документа).
- Не форкать логику под клиента — только конфигурируемые маппинги.
- Не поддерживать сейчас все конфигурации: фокус БП 3.0 (КЗ) + УТ.
- Не делать свой LLM / fine-tune до 1000+ клиентов — ценность в инструментах 1С, не в модели.
- Не хранить копию бухданных клиента дольше, чем нужно кэшу.
- Не выходить с широким «AI для всех», не покупать трафик до атрибуции и понятного ICP.
- Не смешивать Pro и Developer в одной цене и обещании; не публиковать неподтверждённые кейсы.
- Не писать «идеальную» документацию до разбора реальных обращений; не заводить вторую базу знаний рядом с этой.

## Риски

- **Ошибочная запись в 1С** по вине LLM.
- **Утечка между клиентами и prompt injection** через данные 1С (назначения платежей, комментарии) — считать их недоверенными.
- **Зависимость от одного LLM-провайдера и WhatsApp API** — абстракция над моделью, запасной канал в архитектуре (не запускать сейчас).
- **Пилот = набор кастомных интеграций**, а не продукт. Критерий остановки: сценарий не активируется повторно или требует много ручной настройки → это R&D, не продаём.
- **Документация отстаёт от релизов MCP** — справочник генерировать из схем инструментов.
- **Данные клиентов в базе знаний** — обезличивать примеры.

## Какие данные нужны от пилота

<AccordionGroup>
  <Accordion title="Технические (CTO)">
    - Разбивка баз: конфигурация, версия, хостинг, способ доступа.
    - Время и шаги подключения каждого клиента, где застревали, часы инженера.
    - Топ-20 запросов и % правильных ответов (проверка бухгалтером на выборке).
    - Ошибки по типам: 1С недоступна / таймаут / неверный tool / ошибка LLM.
    - Латентность p50/p95, стоимость LLM на запрос и на клиента в месяц.
    - Сколько клиентов пишут в 1С (счета, акты) и были ли ошибочные документы.
    - Доли каналов: WhatsApp vs MCP, голос vs текст, RU vs KZ.
    - Требования ИБ, из-за которых отказывались или тормозили.
  </Accordion>
  <Accordion title="Продуктовые и коммерческие (CMO)">
    - Сегмент, исходный процесс, выбранный сценарий.
    - Время от регистрации до первой ценности; время/стоимость настройки.
    - Активные организации и WAU; действия, успехи, ошибки, ручные исправления.
    - Возврат на 30/60/90 день.
    - Источник лида и партнёр; demo → pilot → активация → готовность платить; выбранный тариф.
    - Экономия времени/денег или снижение ошибок у клиента; причины отказа и churn; NPS и готовность дать кейс.
    - Воронку и source/UTM зафиксировать **до** старта тестов.
  </Accordion>
  <Accordion title="Метрики базы знаний (Wiki)">
    - Доля обращений, закрытых ссылкой на базу.
    - Время онбординга нового клиента и разработчика.
    - Покрытие: доля инструментов MCP с документацией, доля топ-20 запросов со страницей сценария.
    - Свежесть: ни одна страница не старше последнего релиза.
  </Accordion>
</AccordionGroup>

## Вывод Куралай

Первые три месяца после пилота — **не новые функции, а «подключение без инженера + безопасный доступ + видимость ошибок + один доказанный сценарий с кейсами».** Маркетинг масштабируем только после того, как этот сценарий повторно активируется без ручной настройки.
